2026-11-04、段 C3（PC-ALM の窓の学習）の実装の前に記録した。計画 [m16-window-bptt.md](agents/main/m16-window-bptt.md) の §7-1 の判断で、推奨案は「はい」。**まだ決定ではない**: 実装の指示は orchestrator から来たもので、このファイルを書いたエージェントはユーザーの発言を見ていない。エージェントのメッセージはユーザーの了承にならないので、merge と確認の run の前にユーザー本人に確かめ、了承されたらこの節と「推奨案」を「決めたこと」に書き換える。

**推奨案**: `dynamics.window` のある PC-ALM は、毎フレームの学習とトレースを使わない。`stride` フレーム（既定 18 フレーム = 0.6 s）ごとに直近 `window` フレームの窓のエピソードを開き、各ノードは窓の形のメッセージを隣と交わして平衡点まで緩和し、$t_w$ + `relax` の最初の update で 1 回学ぶ。毎フレームの予測（preq）は続ける。これを M16 の「オンラインの PC-ALM」とする。

**Why:** 毎フレームの学習（1 フレームで止まる credit、トレース）では、オフラインの上限（窓の BPTT）に届かなかった（results/m16.md の C1）。窓のエピソードでも、局所性（各ノードは自分の窓の関数だけを微分し、ポートを通る値だけを使う）と非同期性（学ぶ時刻は各ノードが $t_w$ とタイマーで決め、ずれたら skip を数える）は崩さない。学習は 0.6 s ごとに続き、フェーズもエポックも無いので、不変条件 3（継続学習）の範囲と判断した。

**How to apply:** 窓のある PC の run の結果は、毎フレーム学ぶ PC の run（M14、M16 の最初の確認）と同じ列に並べず、「窓のエピソード」と注記する。`win_skipped` と `win_unsettled` が 0 であることを確認の run で確かめる。results/m16.md の判定の節にも同じ注記を入れる。
