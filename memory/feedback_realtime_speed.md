**2026-11-05、実時間で回すための最適化は諦めた（ユーザーの判断）**。ただし「学習が終わらなくなるのは問題」なので、手法や時定数を選ぶときは、今の計算資源（std-00〜03 の 4090、B=128）で確認の run が現実的な時間で終わることを条件にする。目安は、確認の PC-ALM の run（1800 秒の仮想時間、B=128）が 1 台で数時間（7 時間程度まで）で終わること。

**Why:** 2026-11-04 に「B=1（カメラ 1 台）で 60 fps」を目標にして、PC-ALM の時定数を 1 フレーム 5 更新に縮め、CUDA graph と合わせて B=1 で 38.7 fps まで速くした（ユーザーは「あくまで目標なので一旦 OK」）。ところがこの時定数では PC-ALM の学習が安定しなかった。M16 の同時に学ぶ run は 3 seed とも発散し、M15 の確認は `probe_pos_min` が 0.71〜0.93 に落ちた（旧時定数の 16.7 更新/フレームでは 0.96〜0.98）。速さと安定が両立しなかったので、実時間をやめた。

**How to apply:** PC-ALM の時定数は、安定して学べると確かめたもの（16.7 更新/フレーム、h = 2 ms）を使う。CUDA graph（`ctl.cuda_graph`）は結果がビット単位で同じで速くなるだけなので残す。B=1 の fps は測らなくてよい。新しい設定を確認に回す前に、B=128 の fps から 1 run の所要時間を見積もり、長すぎれば run の長さや設定を見直す。経緯は `exp/video/results/m16.md` の速さの節。[[project-m16-pc-window-episodes]]
