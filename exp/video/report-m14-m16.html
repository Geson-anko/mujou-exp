M16 · 速さ

更新を減らして速くすると、PC-ALM が安定しない

カメラ 1 台で 60 fps を目標に、PC-ALM の更新を 1 フレーム 5 回に減らし、ノードの計算を CUDA graph で再生すると、速さは 8.5 fps から 38.7 fps に上がりました。ところがこの設定では、M16 の同時に学ぶ run が 3 seed とも発散しました。実時間で回す最適化はやめ、16.7 回の更新に戻しました。

1

実験の仕組み

M16 のモデルは画像を潜在 z に写すエンコーダと、z の並びから次の z を予測する動力学からできています。エンコーダ（ViT）は JEPA の損失と、z から画像を戻す再構成の項だけで学びます。動力学（minGRU）の予測誤差はエンコーダへ戻りません。PC-ALM では z を送るだけのポートで、BP では detach でこれを保証します。

図の四角と、その中を点線で区切った区画の 1 つ 1 つがノードです（zk の四角は送るだけのポートです）。各ノードは非同期に動き、隣のノードとのずれだけから重みを学びます（mujou の PC-ALM）。比べるために、同じネットワークを BP で学ぶ版も回しました。M14 ではエンコーダを外し、玉の状態から作った観測を直接動力学に入れます。M15 では動力学を外します。

指標の読み方

開ループ
評価の窓で 16 フレームを観測し、そこから先は自分の予測を入力に戻して h フレーム先まで予測します。h = 5・10・20 を測ります。
roll{h}/cv{h}
M14 の指標です。h フレーム先の予測の二乗誤差を、等速の外挿（最後の 2 フレームの差を速度として進める）の誤差で割った比です。小さいほど良く、条件は 0.5 未満です。
probe_pos_min
M15 の指標です。z から 3 つの玉の位置 (x, y) への線形回帰の R² の最小です。1 に近いほど良く、条件は 0.9 以上です。M16 の動力学は z を線形に読むので、位置が線形に読めることを受け渡しの条件にしました。
後から学ぶデコーダ
各チェックポイントでエンコーダを止め、z から画像へのデコーダを別に学びます。動力学が予測した z を画像に戻して見るための道具で、システムには入れません。
img_roll{h}
M16 の指標です。予測した z を後から学ぶデコーダで戻した画像と、真のフレームとの画素あたりの二乗誤差です（画素は 0〜1）。平均の画像（pix_mean、約 0.0147）と写し（最後の観測のフレーム、pix_copy）の両方を下回るのが条件です。
rec_roll{h}/pix{h}
学習中に、学習に使っている再構成のデコーダで測った同じ誤差を、平均の画像と写しの小さい方で割った比です。1 未満なら両方を下回ります。設定の探索に使いました。
窓の BPTT
各ストリームの直近 36 フレームの z を覚え、18 フレームごとに、16 フレームを観測して 20 フレームを開ループで予測する窓の損失で 1 歩学びます。時間を通して勾配を流します（BPTT）。

判定に使うのは玉の合成動画です。半径 0.06・0.08・0.10 の 3 つの玉が、重力の下で壁と床に跳ね返ります（反発係数 1、抵抗 0）。玉どうしはぶつからずにすり抜けます。32×32 の灰色の画像で、128 本のストリームを並べて流します。玉の真の状態があるので、予測の答え合わせができます。下の M16 の図の各窓の上の行が、この入力です。

4 · M14

状態を観測にすれば、動力学はオンラインで学べるか

エンコーダを外し、玉の位置を観測として動力学に入れました。段 1 は玉 1 つ、段 2 は玉 3 つです。速度は見えないので、動力学は状態 s に履歴から速度を推して持つ必要があります。30 分（54000 フレーム）のストリームで学び、最後の評価を test のクリップで測りました。

12 本すべてが条件を満たしました。5 フレーム先は等速の外挿の 0.34〜0.44 倍、10 フレーム先は 0.17〜0.30 倍です。1 ノードでは、PC-ALM の平衡点の credit は BP の勾配そのものなので、値が一致します。

オフラインの上限（Adam で窓を時間を通して学ぶ）では、時間を通した credit の有無で差が大きく出ました。段 2 の大きい動力学で、BPTT の 5 フレーム先は 0.12、1 フレームで切ると 1.20 です。オンラインでは、適格度トレースがこの credit を近似します。段 2 でトレースを外すと、最良の設定でも 1.15〜1.20 でした。

観測を 32×32 の画素にした段 3 は届きませんでした。test で、5・10 フレーム先の誤差は等加速度の外挿の 2.2 倍・1.9 倍です（条件は 0.5 倍未満）。オフラインの上限でも 1.6 倍・1.5 倍でした。入力が観測の線形写像の動力学では、1024 画素から玉の位置を取り出す非線形の写像を持てません。下の図のように、予測は数フレームでぼけて塊になります。画素から位置を取り出すのはエンコーダの役目として、M15・M16 に回しました。

5 · M15

視覚の損失だけで、玉の位置が線形に読める z を学べるか

動力学を外し、ViT のエンコーダを JEPA の損失（マスクした patch の潜在を予測する + SIGReg）で学びました。最初の探索（32 trial）では、1800 秒まで走った trial でも probe_pos_min は 0.51 が最高でした。preset のまま 600 秒学んだ run を調べると、学ぶほどトークンからも玉の情報が消えていました。マスクで隠れた玉は文脈から当てられないので、エンコーダは玉を表さない方向へ動きます。M13 で潜在空間が歪んだのと同じ向きです。

そこで、z から最後のフレームを戻す再構成の項を足しました。普通の MLP のデコーダでは、z は玉を描き戻せても、位置が線形の関数になりません。z を各画素に並べ、画素の座標と合わせて値を出す spatial broadcast decoder に替えると、位置が線形に読めるようになりました。

broadcast の μ=100 は 2 seed とも 0.90・0.94 に届きました。このまわりを探索し、#13（μ=22、AdamW 2.0e-4）を選びました。これを PC-ALM と BP の seed 0/1/2 で確かめます。

6 本とも 0.957〜0.979 で条件を満たしました。PC-ALM と BP の値は近いものの、一致はしません（エンコーダは 2 ノード）。Walking Tours では、z から 8×8 の灰色の縮小画像への線形の R² が 0.86（N=1）・0.87（8 フレームのまとまり）で、学習前の ViT（0.25・0.15）を大きく上回りました（BP、seed 0、判定には使わない）。

6 · M16

エンコーダと動力学を同時に学び、予測を画像に戻して当たるか

M15 のエンコーダと M14 の動力学を 1 つの run で同時に学びました。動力学はエンコーダの z の次を予測するだけで、エンコーダに credit を送りません。同じ seed と GPU の種類なら、エンコーダの重みは M15 の視覚だけの run とビット単位で同じになります（テストで確かめた）。

最初の確認では、BP の 3 seed とも 10 フレーム先の画像の誤差が平均の画像の 1.3〜1.5 倍でした。study の目的を画像の比に替えて探し直しても、下の図の灰色の線のように 1.2〜1.3 倍で止まります。

原因を分けるため、エンコーダを固定して動力学だけをオフラインで学びました。窓を時間を通して学ぶ（BPTT）と、10 フレーム先は平均の画像の 0.39 倍まで下がります。1 フレームで切ると、大きい動力学でも 1.35〜1.42 で止まりました。z と動力学の大きさは足りていて、律速は時間の credit です。適格度トレースは自分の再帰だけを通す近似で、開ループで戻した予測を通る credit を落とします。

そこで動力学を窓の BPTT で学ぶ形に替えました。窓の中で戻した予測を通る勾配（feedback=grad）だけが条件を満たし、戻した予測で勾配を切る版（detach）や真の z を入れる版（teacher）は、10 フレーム先で 1 を超えるか発散しました。PC-ALM では、各ノードが自分の窓の関数だけを微分し、窓の形のメッセージで credit を運びます。平衡点では BP の窓の勾配と一致します（float64 で 1e-10）。

窓の BPTT では、BP の 3 seed とも 5 フレーム先が平均の画像の 0.38〜0.44 倍、10 フレーム先が 0.66〜0.75 倍で、条件を満たしました。PC-ALM も 0.41〜0.46 倍・0.70〜0.79 倍で満たします。同時に学ぶ run の probe_pos_min は、M15 の確認の run と表示の 4 桁まで一致しました（PC-ALM は 0.9742・0.9567・0.9787、BP は 0.9747・0.9656・0.9753）。動力学はエンコーダに credit を送っていません。

エンコーダを固定した対照は、10 フレーム先で同時に学ぶ run より良く、比は約 0.5 です。同時に学ぶ run は、エンコーダがまだ学んでいる間の z でも動力学を学ぶので、その分を損します。

7 · M16

カメラ 1 台の入力を実時間で学べるか

ここまでの run は仮想時間で回していて、壁時計の速さは問いませんでした。ユーザーはカメラ 1 台（B=1）のストリームを学習込みで 60 fps、つまり 30 fps の動画の 2 倍の速さで回すことを求めました。PC-ALM は 1 フレームの間にノードの更新を何度も繰り返すので、BP より重くなります。

1 フレームあたりの更新を 16.7 回から 5 回に減らすと、PC-ALM は 8.5 fps から 19.4 fps になりました。これに合わせて時定数を変え、窓のメッセージが落ち着く時間（0.53 秒）が窓の間隔（0.6 秒）に収まるようにしました。さらに視覚・動力学・JEPA ヘッドのノードの計算を CUDA graph で再生すると、38.7 fps になります。実時間（30 fps）は超えましたが、目標の 60 fps には届いていません。

時定数を変えたので、M15 と M16 の PC-ALM の確認を 5 回の更新で回し直しました。M15 の視覚だけの run では SIGReg が跳ね、probe_pos_min が 0.93・0.72・0.91 に落ちました（16.7 回では 0.96〜0.98）。M16 の同時に学ぶ run は、3 seed とも予測の誤差が有限でなくなって止まりました。BP は時定数を変えても条件を満たしました。

速さと学習の安定が両立しなかったので、ユーザーの判断で実時間で回す最適化はやめ、16.7 回の更新に戻しました。CUDA graph は結果を変えないので残しています。代わりに、今の計算資源で学習が終わることを守ります。4090 で B=128 の確認の run（30 分の仮想時間）は、BP が 30 分、PC-ALM が 1 台を占めて 3.5 時間で終わります。
