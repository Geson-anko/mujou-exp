# 視覚と動力学の同時の学習（M16、2026-11-03〜）

[README](../README.md) の結果の 1 節。MILESTONES.md の M16。M15 のエンコーダ（視覚の損失だけで学ぶ）と M14 の動力学（エンコーダの $z$ の次を予測する）を、1 つの run で同時に学ぶ。動力学の予測誤差はエンコーダに credit を送らない（`programs/joint.py`）。

実行は fleet（`exp/lib/fleet/README.md`）。preset は `exp/video/conf/experiment/m16/`、表は `just fleet table`（`exp.lib.runs`）。

## 設定

- **データ**: M15 と同じ 3 つの玉（半径 0.06・0.08・0.10）を 32×32 に描いた動画、B=128 のストリーム、$N=1$
- **視覚**: M15 の受け渡しの設定（`m15-balls-n1-broadcast-bp-v1` の #13: `vit_t`、patch 4、JEPA と spatial broadcast decoder（幅 64）による最後のフレームの再構成の項 $\mu=22$、sg なし、SIGReg はトークンに 0.056、マスク 0.5、AdamW 2.0e-4、warmup 60）
- **動力学**: 小（M14 の段 2 と同じネットワーク）。入力と目標は $z$（128 次元）で、M14 の観測（6 次元、標準化済み）と尺度が違うので、M14 の段 2 の #45 から始めて、optimizer の値とトレース・残差・`open_loop` を BP の study（seed 100/101、val、目的は `roll10/mean10`）で選び直した。選んだのは #14（トレースなし、AdamW 6.6e-5、`tau_m` 0.33、`tau_v` 12、warmup 300、残差、`open_loop` 0.5）
- **学習**: PC-ALM と BP。動力学の誤差はエンコーダへ戻らない（PC-ALM は `z_out` が送るだけのポート、BP は detach）。同じ seed とデータでは、エンコーダの重みは M15 の視覚だけの run とビット単位で同じになる（`tests/video/programs/test_joint.py::TestNoCreditToTheEncoder`）
- **対照**（`m16/balls_frozen`）: エンコーダを、同じ設定・seed・学習則の M15 の確認の run の最後のチェックポイントに固定し、動力学だけを学ぶ
- **評価**（`measure.every` 秒ごと）: 視覚の行（M15 と同じ probe、実効ランク、`z_spread`）と、固定した窓（16 フレームを観測し、そこから開ループで予測）の潜在の誤差 `roll{h}`、`copy{h}`（最後の $z$）、`mean{h}`（平均の $z$）
- **後から学ぶデコーダ**（`task=posthoc`）: 各チェックポイントで $z$ から画像へのデコーダを学び、動力学が予測した $z$ を画像に戻す。画素の誤差 `img_roll{h}` を、写し（最後の観測のフレーム、`pix_copy{h}`）と平均の画像（`pix_mean{h}`）と比べる。`img_recon` は観測した $z$ を戻した誤差で、デコーダの下限の目安
- **コード**: snapshot と mujou（`881c4ee`）の SHA は各節に書く

## 二度目の探索（`m16-balls-joint-img-bp-v1`）

- **学習中の画像の評価**（`programs/joint.py`）: 視覚の再構成の項のデコーダ（spatial broadcast decoder、学習に使っているもの）で、動力学が予測した $z$ を画像に戻す。キーは `rec_roll{h}`、`rec_recon`、`pix_copy{h}`、`pix_mean{h}`、`rec_roll{h}/pix{h}`（= `rec_roll{h}` / min(`pix_copy{h}`, `pix_mean{h}`)）。後から学ぶデコーダ（`img_*`）とは別のキーにする。評価だけで、学習の状態は変えない

### 結果（1800 秒の val、seed 100・101）

完了した trial はどれも、5 フレーム先では平均の画像を下回った（`rec_roll5/pix5` 0.65〜0.75。最初の確認では平均の画像とほぼ同じ）。10 フレーム先は、設定によらず 1.2〜1.3 で止まる（目的の最良は #33 の +0.21: 大、トレース、AdamW 9.2e-5、`tau_m` 0.38、`tau_v` 90、warmup 60、残差、`open_loop` 0.25）。上位は大とトレースの組。時間の変化を見ると、`rec_roll10/pix10` は 300 秒から先は下がらない。`roll1/copy1` は 420 秒ごろの 0.46〜0.55 から 1800 秒の 0.62〜0.66 へ悪くなる（エンコーダが鋭くなるにつれ、1 フレームでの $z$ の変化 `copy1` が大きくなる）。失敗した 3 trial（#43・#50・#51）は、4060 に詰め込んだときの起動時の `CUBLAS_STATUS_ALLOC_FAILED` で、設定のせいではない。

## 窓の BPTT（計画: `memory/agents/main/m16-window-bptt.md`）

オンラインの動力学を、ノードの中の窓の BPTT で学ぶ。各ストリームの直近 $W=36$ フレームの $z$ を覚え、$S=18$ フレームごとに、$s=0$ から 16 フレームを観測し 20 フレームを開ループで予測する窓の損失（オフラインの上限と同じ `window_loss`）で 1 歩学ぶ。BP は 1 つのノードの中の autograd、PC-ALM は各ノードが自分の窓の関数だけを微分し、窓の形のメッセージで credit を運ぶ（平衡点で BP の窓の勾配と一致する）。毎フレームの学習とトレースは使わない。

### C1: ストリームの順の上限（`m16-c1-v1`、`task=offline`、`offline.order=stream`、val、snapshot `d45bc7f`）

オンラインの run が学ぶのと同じ窓を同じ順に、オンラインの optimizer（`make_optimizer`、1 窓あたり Adam(1e-3, 0.9, 0.999) と同じ: lr 1e-3/S、`tau_m` = 0.6/−ln 0.9 s、`tau_v` = 0.6/−ln 0.999 s、warmup 0）で学ぶ。エンコーダは M15 の確認の seed 0（BP と PC-ALM）に固定。

| run | 設定 |
| -- | -- |
| a | S=18（2999 ステップ）× feedback ∈ {grad, detach, teacher}、BP と PC-ALM のエンコーダ |
| b | S=36（1499 ステップ）× {grad, detach}、BP のエンコーダ |
| c | `order=random`（batch 128、Adam 1e-3）で a と同じステップ数、detach |
| d | `credit=own`（トレースと同じ打ち切り）、S=18、detach（帰属の診断。判定には使わない） |

**判定**（回す前に決めた、最後のステップの値）:

1. ある feedback が、BP と PC-ALM の seed 0 のエンコーダの両方で `rec_roll5/pix5` ≤ 0.85 かつ `rec_roll10/pix10` ≤ 0.95 を満たせば、BP の窓の学習を作る。どれも満たさなければ止め、大きさや損失の重みを見直す
2. 満たすもののうち、10 フレーム先で最良から 0.03 以内の、いちばん単純なもの（teacher、detach、grad の順）を選ぶ

4. 選んだ設定を、BP と PC-ALM の seed 1・2 のエンコーダでも回す。どれかが 10 フレーム先で 1 を超えたら、PC-ALM を作る前に見直す
5. d も 0.95 以下なら、効いたのは「$s=0$ からの窓という目的」で、層をまたぐ時間の credit ではないと書く。d が 1.2 前後なら、効いたのは時間を通した credit と書く

### C3: PC-ALM の窓の学習（実装、設計: `memory/agents/main/m16-pc-window-design.md`）

PC-ALM の各ノード（`Dynamics`、`DynamicsLayer`、`Compare`）が、窓のエピソードで BP と同じ規則を学ぶ（`dyn.nodes.DynamicsBlock`）。0.6 秒ごとの窓のエピソードを M16 の「オンラインの PC-ALM」とするかは未決定で、推奨案を [memory](../../../memory/project_m16_pc_window_episodes.md) に記録した（ユーザーの了承待ち）。窓のある PC の run は、毎フレーム学ぶ PC の run と同じ列に並べない。

- 各ノードは自分の窓の関数（minGRU の `scan`、または readout）だけを、受け取った detach 済みの窓から微分する。開ループの位置は `Compare -> Dynamics` の予測のポートの反復で解き、grad では戻した予測の credit も同じポートで返す
- 平衡点で各ノードの $g_\theta/(BP)$ は `window_loss` の勾配の対応する部分と 1e-10 で一致する（float64、`tests/video/dyn/test_window_pc.py`）。3 窓の軌跡は BP と 1e-8 で一致する
- 既定の窓（W=36、O=16、grad、3 ノード）では、メッセージは $t_w$ の 80 period 後（0.16 秒）にビット単位で落ち着く。relax 0.3 秒（150 period）で学ぶ。1 窓あたりの窓の関数の計算は 4 ノードで約 318 回
- 落ち着いたかはメッセージのビット単位の比較で決まる。GPU の計算が決定的でないと落ち着かず、毎 update 計算して `win_unsettled` を数える。確認の run の前に 4090 で `task=bench`（`m16/balls_joint_win`、learner=pc）を回し、fps・1 窓あたりの `win_vjps`・`win_unsettled`=0 を確かめる
- **速度**（CPU、`task=bench` を 2 秒、`m16/balls_joint_win` の大きさで B=16）: PC-ALM は窓ありが 1.25 fps、毎フレームの学習が 1.32 fps。BP は窓ありが 11.8 fps、毎フレームが 11.7 fps。窓の学習による PC の遅れは約 5%。4090、B=128 の値は確認の run の前に測る
- `win_unsettled`（落ち着く前に学んだ窓の数）は、ノードが自分の入力の変化だけから決める目安で、木の順（`ManualRun` と `Host`、この実験のすべての run）か周期の比が 2 以内のときに正しく数える。不規則な更新の順では、0 でも勾配が正しいとは言えない（監査の乱数のスケジュールで、数えずに誤った勾配で学ぶ場合があった）

- 同時に学ぶ PC-ALM は 3 seed とも、予測の誤差（preq）が有限でなくなって止まった。seed 0 の視覚は、止まる前の 1200 秒まで M15 の run と同じ値をたどる（動力学は credit を送らない）ので、崩れたのは動力学の側。seed 2 は 480 秒の val で 10 フレーム先の潜在の誤差が平均の 733 倍になった
- エンコーダを固定した対照は完走したが、デコーダの下限（`img_recon`）が BP の 0.0004 の 3.5〜11.5 倍に悪化した。崩れかけたエンコーダの $z$ からは画像を戻しにくい
- BP は時定数を変えても条件 2 を満たした。ただし同時に学ぶ BP の `probe_pos_min` は二度目の確認（0.9747・0.9656・0.9753）と一致しない。BP の run も時定数で値が変わる（BP のノードの更新も `time` の周期で回る）。CUDA graph のせいではないことは、下の再実行で確かめた
- 結論: 速さ（B=1 で 38.7 fps、下の節）と学習の安定が両立しなかった。2026-11-05、ユーザーの判断で実時間で回す最適化はやめ、今の計算資源で学習が終わる速さを守ることにした（[memory](../../../memory/feedback_realtime_speed.md)）。preset は二度目の確認の時定数に戻した。CUDA graph は結果を変えないので残した
