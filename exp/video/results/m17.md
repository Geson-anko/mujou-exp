[README](../README.md) の結果の 1 節。MILESTONES.md の M17。再構成の項を使わない JEPA（V-JEPA・V-JEPA 2 の入力とマスク、LeJEPA の SIGReg）で、128×128×3・30 fps の Walking Tours のエンコーダを PC-ALM と BP で学ぶ。$z$ からの再構成、予測器を通した復元、$z$ の上の線形の動力学は、エンコーダを止めて後から測る（`task=posthoc`、`measure/encoder_eval.py`）。

この節は回す前に決めたことから書き始める。数字は物差し・試し・study・確認の順に、回した後で足す。

## 設定

- **データ**: `3c3e6805fdaa`（中央の正方形を 128×128 に縮めた、30 fps のまま）。Zurich を評価だけに使い（calib・val・test）、残りの 9 本で学ぶ
- **時間の対応**: run の 1 フレーム（`time.frame`、仮想時間の 1/30 秒）に、ストリームは動画を 3 フレーム（0.1 秒）進める（`data.tours.advance=3`）。動画は仮想時間に対して 3 倍速で流れ、間の 2 フレームはどのノードも推論しない。「30 fps のストリームで 3 フレームに 1 回学ぶ」の 1 つの実現で、同期は持ち込まない

- **損失**: JEPA の予測誤差と SIGReg だけ。`vision.recon` は 0 に固定。EMA のターゲットは使わない
- **バッチ**: preset の `data.streams` は 32 で、計画の B=128 と違う（`task=bench` で決める暫定値）。SIGReg の統計量は有効な sample 数とともに大きくなるので、B を変えると同じ $\lambda$ でも SIGReg の強さが変わる。確認の run で B を変えるなら、$\lambda$ を探し直すか、ここに書く

## 実装で決めたこと（回す前、2026-11-12）

レビューを受けて、study の前に次を決めた。

### 見える patch の数

マスクはブロックの和集合を守る。見える数は sample ごとに固定（形をそろえるため）で、和集合が残す見える数の下側 4 分位点にする（`masks.expected_keep`）。和集合がそれより少なく残す sample は引き直し（8 回まで）、多く残す sample は余分な見える patch を無作為に隠す（V-JEPA の collator が batch の最小に切り詰めるのと同じ向き）。8 回とも足りない確率は 1.5e-5 以下で、そのときだけ隠した patch を見せる。

| view | 和集合の見える数の平均 | 見える数（空間 64 のうち） | 計画の見積もり |
| -- | -- | -- | -- |
| 短い範囲（8 × 0.15） | 21.4 | 18（28%） | 27% |
| 長い範囲（2 × 0.7） | 9.6 | 8（12.5%） | 9% |

最初の実装は見える数を平均（21 と 10）にそろえていた。和集合が足りない約半分の sample で、隠したはずの patch を無作為に見せていた（長い範囲では context の約 4 割がブロックの中に散らばる。tube なので全フレームで見える）。BP と PC-ALM に同じく効くので比較は公平だったが、予測の課題が易しくなり、ユーザーの規則（ブロックの和集合）から外れていた。

### 探索の目的

$$
J = \log \max\left(\frac{\mathrm{recon}}{\mathrm{recon}_{\mathrm{PCA}}},\ \frac{r_1}{r_{1,\mathrm{PCA}}}\right),\quad r_1 = \mathrm{dyn}_1 / \mathrm{copy}_1
$$

上限は $\log 10$ で、崩壊（`z_spread` < 1e-3）・値の欠け・非有限も $\log 10$。sweep の発散した seed（`DIVERGED`）と同じ値で、PCA の 10 倍悪い符号は崩壊・発散と同じ順位になる（それより下にはならない）。

計画（MILESTONES.md）の式 $\max(\mathrm{recon}/\mathrm{recon}_{\mathrm{PCA}},\ \mathrm{dyn}_1/\mathrm{dyn}_{1,\mathrm{PCA}})$ から 2 か所を変えた。

1. **対数にした**: 最初の実装は比のまま、上限を $\log 10 = 2.30$ で切っていた。比が 2.3 を超える trial は、崩壊した trial や発散した seed と同点になる。smoke では、学習前の ViT と 4 秒学んだ ViT の比がどちらも約 3.7 で、上限に張り付いていた。対数にすると、比 10 までの trial は区別される
2. **動力学の項を写しとの比にした**: PCA の符号は最後の 1 枚から作るが、ViT の $z$ は $N$ 枚の積みから作る。隣り合う積みは $N-1$ 枚を共有するので、積みを読む符号はどれも構造上なめらかで、`dyn_1`（$1-R^2$）が小さく出る。smoke の学習前の ViT の `dyn_1` は 0.0026 で、PCA の 0.061 の 1/23 だった。このままでは $\max$ の動力学の項が効かず、$J \approx \mathrm{recon}/\mathrm{recon}_{\mathrm{PCA}}$ になる。写しの誤差 `copy_1` で割ると、入力の重なりが打ち消される

完了の条件の「`dyn_1` が同じ $D$ の PCA を下回る」も、この交絡のために学習しなくても満たされる。判定では `dyn_1/copy_1` で PCA と比べ、`dyn_1` は同じ積みを見る学習前の ViT と比べる。

### PCA との比べ方の補い

- **デコーダの入力の標準化**: $z$ のデコーダは学ぶ 9 本の $z$ の成分ごとの平均と標準偏差で標準化した $z$ を受け取る。PCA の上位の成分は標準偏差が数十になり、SIGReg で単位の尺度に近い ViT の $z$ と最適化の条件が違っていた。PCA の線形の再構成 `recon_lin` を物差しの行にあわせて載せる
- **白色化した動力学の誤差**: `dyn_h` は全成分の誤差の和を全分散で割るので、分散の大きい成分がゆっくり変わる PCA に有利に出る。SIGReg は $z$ を等方的にするので、速く変わる成分も同じ重みで数えられる。学ぶ側の $z$ の共分散で白色化した座標の誤差 `dynw_h`・`copyw_h` を併記し、PCA と比べるときに使う（$z$ の可逆な線形変換で変わらない）。目的の定義は変えない
- **stride ごとに分ける**: study の `vision.stride` は {2, 3, 6} で、$\Delta$ と一緒に動力学の 1 ステップも 0.067・0.1・0.2 秒に変わる。PCA の物差しは trial ごとに同じ stride で測るので比は部分的に正規化されるが、trial の間で比べている課題そのものが違う。結果は stride ごとの `dyn_1` を分けて載せ、上位を選ぶときに stride が違う trial を同じ土俵で並べていると書く
- **calib と val の近さ**: calib・val・test は、`eval_windows` が Zurich から無作為に選んだ slot を 3 つに分けたもの（M15 と同じ）。時間的に隣り合う slot が calib（ridge の $\alpha$ を選ぶ）と val（目的）に分かれると、ほぼ同じ場面が両方に入りうる。$\alpha$ を calib で選ぶので、val の `dyn_h` は少し楽観的に出うる。test も同じ扱い
- **エンコーダが止まっていること**: posthoc の前後で、エンコーダ・予測器の state_dict がビット単位で変わらないことをテストで確かめる（`tests/video/measure/test_encoder_eval.py::TestEncoderEval::test_the_encoder_is_held_bit_for_bit`）

### 補完の誤差（2026-11-12 に足した指標）

方針の見直し（MILESTONES.md の M17）を受けて、held-out の補完の誤差を指標に足した（`measure/completion.py`）。学習の損失は変えていない。

- **定義**: 隠し方ごとに、隠したトークンの集合 $\Omega$ について $E = \sum_\Omega \lVert \hat s - s \rVert^2 / \sum_\Omega \lVert s - \bar s_\Omega \rVert^2$（$1 - R^2$）。$\hat s$ は学習と同じ道（見えるトークンだけをエンコーダに通し、予測器で当てる）の予測、$s$ は積み全体を同じ重みに通した target のトークン。分母は隠したトークンの分散なので、トークンを縮めても $E$ は下がらない（損失 `pred` は下がる）。$\bar s_\Omega$ を当てると 1、完全に当てると 0
- **隠し方**: `short`・`long`（学習と同じ context view。split ごとに固定のマスク）と `future`（最後の 4 分の 1 の時間の slot のトークンをすべて隠す。$N=16$ では最後の 2 slot = 0.4 秒、$N=8$ では 1 slot。$N=1$ には無い）
- **鍵**: `comp_<kind>`（予測器）、`comp_<kind>_vis`（その積みの見えるトークンの target の平均で当てたもの。見えるトークンは target view の中で隠した位置にも attention しているので、甘い物差し）、`comp_<kind>_mean`（学ぶ 9 本の held-in の積みの target のトークンの、次元ごとの平均で当てたもの）
- **どこに出るか**: run の `evals.jsonl` の val・test の行（split 自身の値）。val の行には calib（`calib_comp_*`）と、学ぶ 9 本から取った固定の held-in の積み（`fit_comp_*`、`encoder_eval.stream_windows` の 256 窓、マスクは seed 2718）も載せ、held-in と held-out の差を見る。`baselines.json` の `init_comp_*` は学習前のネットワーク。posthoc の `metrics.jsonl`（`vit`）と `baselines.jsonl`（`init`。PCA には予測器が無いので無い）にも同じ鍵が出る。TensorBoard では `eval/<split>/comp_*`・`post/<split>/comp_*`・`base/<split>/init/comp_*`
- **目的**: 既定は今の $J$ のまま。`measure.encoder_objective=completion` を選ぶと、val の `comp_<kind>` の平均の対数を目的にする（崩壊・非有限は $\log 10$）。新しい目的の式はまだ決めていないので、暫定の選択肢として置いた
- 今の目的には $z$ の水準の予測が無いので、その $1 - R^2$ はまだ無い。$z$ の予測を足すときに一緒に足す（足した: 下の節の `zcomp_<view>`）

### 監査を受けた直し（2026-11-12、回す前）

試しの run の no-go を受けた監査（mini_train の再現、diag_ckpt）で、崩壊の原因は学習率・warmup・データの順序ではなく目的の式だと分かった。preset の損失（SIGReg を $z$ だけに、sg も EMA もなし）では、トークンをクリップごとの定数にして、context の平均で隠したトークンを当てるのが最適点に近い。i.i.d. の batch でも lr 1e-5 でも同じ崩壊が起きた。直したものと、実験で試せるようにしたもの:

- **補完の誤差の正規化**（不具合）: `comp_<kind>` の分母には積みの間の広がりも入るので、トークンが積みの中でつぶれても小さく出ていた。積みの中の広がりで割る `ncomp_<kind>`（`_vis`・`_mean` も）を足した。崩壊の監視として、行に `tok_within`（積みの平均トークンからのずれ）、`tok_between`（積みの平均トークンの split の中の分散）、`tok_temporal`（同じ空間位置の slot の間のずれ。slot が 2 つ以上のとき）も載せる
- **トークンの崩壊の防止**（不具合）: `vision.token_sigreg` で SIGReg のかけ方を選ぶ。`scaled`（今までどおり、$T$ で割る）、`raw`（割らない）、`clip`（積みの平均を引いたトークン、割らない）。`wt_n16`・`wt_n8`・`wt_n1` の preset は `sigreg_on: both`・`token_sigreg: clip` に直した。preset の損失が、つぶれたトークンより広がったトークンを選ぶことをテストで確かめる（`test_m17_tokens_constant_within_a_stack_are_not_an_optimum`）。直す前の preset はこのテストに落ちる
- **評価の batch**: 損失と SIGReg を出す batch を、split の窓を固定の順に混ぜて組む（`PackedMeasures.order`）。時刻順では 1 本の動画の数分から batch ができ、val の SIGReg が高く出ていた。行の `loss`・`pred`・`sigreg` の値はこの直しで変わる（`rank`・`z_spread`・補完の誤差は変わらない）
- **長い範囲の view の見える数**: 上の表を 6 から 8（12.5%）に直した

レシピとの差は、どれも既定では今までどおりで、設定で選べる:

| 設定 | 内容 |
| -- | -- |
| `optim@optim_vision=adamw_step` | step で数える AdamW（`exp.lib.optim.StepAdamW`、`torch.optim.AdamW` と一致）。`lr` は 1 step あたり、`betas`、`weight_decay`（2 次元以上のパラメタだけ）と `weight_decay_end`（`decay_steps` まで線形）、`warmup_steps`（学習率だけを線形に上げる）、`decay`（`constant` か `cosine`、`min_lr` 倍まで）、`clip`（ノードの勾配のノルム）。preset の値は 7.5e-5、warmup 1800 step、cosine で 18000 step（600 秒）に 1e-3 倍、wd 0.05 |
| `vision.pred_dim`・`vision.pred_heads` | 予測器のブロックの幅と head（V-JEPA の細い予測器）。深さは `vision.pred_depth` |
| `vision.target_norm` | 予測の target を affine なしの LayerNorm に通す（I-JEPA・V-JEPA の公式コード） |
| `vision.ema` | 対照（BP だけ）。予測の target を、この momentum のエンコーダの EMA のトークンにする。M17 の規則では使わない。PC-ALM では設定できない |
| `data.tours.sampling=iid` | 各フレームの積みを、9 本の動画の一様に独立な位置から取る（i.i.d. の対照、`IIDStackedTourFrames`）。同じノード・モデル・損失・optimizer のまま、オフラインの shuffle した batch の学習になる |

### 時空間の補完（2026-11-12 に足した目的）

ユーザーの方針（課題は時空間の補完、再構成の項なし、LeJEPA の形でもよい）を、損失の選択肢として入れた（`jepa/loss.py`）。

- **時空間の view**: context の view に `future` を足せる（`{blocks: 8, scale: 0.15, future: 2}`）。最後の `future` 個の時間の slot をまるごと隠すので、その view は過去だけを、ブロックの外だけ見る。`blocks: 0` なら過去を全部見る。見えるトークンがブロックの中にも未来にも無いことをテストで確かめる
- **$z$ の水準の補完**: 各 view の pool $z_v$ を projector に通して $u_v$ とし、context の view の $u_v$（任意で view の種類つきの小さな予測器 $q$）が、積み全体の $u_g$ を当てる。$L = (1 - \lambda)(\beta L^{\mathrm{pred}} + \alpha L^z) + \lambda S$。設定は `vision.z_weight`（$\alpha$）、`vision.token_weight`（$\beta$、0 ならトークンを当てない）、`vision.projector`（各層の幅、最後が出力）、`vision.zpred_hidden`（$q$ の幅、0 なら $q$ なし）。`vision.sigreg_on=views` は view ごとの $u$ の SIGReg（LeJEPA）、`views_tokens` はそれとトークンの SIGReg の平均。損失はすべてヘッドのノードの中にあり、PC-ALM のエンコーダのノードの `lam` が BP の credit と一致することをテストで確かめる。posthoc の特徴量 $z$ は今までどおり（projector の前）
- **指標**: 行に `zcomp_<view>`（held-out の $u_g$ を各 context view から当てる $1 - R^2$。projector が無ければ $z$ そのもの）と、$\alpha > 0$ なら `zpred`（損失のその項）を載せる
- **preset**: `m17/st_n16`（3 つの context view: 短い範囲、長い範囲、過去。$\beta = 0$、`sigreg_on: views`、projector [512, 512, 64]、SIGReg 512 方向、`adamw_step`）と、`m17/st_tok_n16`（同じものに、トークンの予測を $\beta = 0.5$、target は LayerNorm、`views_tokens`・`token_sigreg: clip`）

### 基準の課題（診断のコード）

`exp/video/diag/imagenette.py` は、レシピの §3 の基準の課題（LeJEPA の minimal を Imagenette で）を回す診断のコードで、run の program ではない。`prep` は Imagenette（`imagenette2-160`）の JPEG を ffmpeg で 128 px の u8 にする。`train` は M17 の ViT を画像（64 トークン）で BP と `StepAdamW` で学び、学習前から `--every` step ごとに val の線形 probe（ridge、one-hot）の正解率を `log.jsonl` に書く。`--mode lejepa` は LeJEPA の minimal（拡張した view、projector、view ごとの SIGReg。段階 S2）、`--mode masked` は M17 の packed の形をそのまま画像に（`--objective tokens` はトークンの予測と `clip` の SIGReg、`z` は $u_g$ の補完。段階 S3、EMA なし）。合格の目安は、学習前の probe から 30 ポイント以上。まだ回していない

## 判断（2026-11-12）: study と確認に進まない（no-go）

- **$N$ と run の長さ**: $N=16$・B=32・600 秒（PC-ALM の見積もり 5.8 時間 < 7 時間）。$N=8$ に落とす必要はない。ただし下の理由で、確認の run はまだ回さない
- **no-go の理由**: preset の JEPA（BP）は $N$ = 16・8・1 のどれでも、学ぶほど学習前の ViT より悪くなる（val の `recon` 0.63〜0.66 → 0.75〜0.81、`dyn_1/copy_1` 0.48〜0.84 → 0.95〜1.0）。規則の中で試した 9 つの変更（SIGReg の重み・かけ先、学習率、マスク、sg、B）でも、学習前を下回る設定は無かった。今の探索空間（`studies/m17_wt_bp.toml`）はこれらの軸の組み合わせなので、32 trial の study で判定基準（`recon` < 0.180 は学習前の 0.713 の 1/4）に届く見込みは低い。BP で届かない設定を PC-ALM で確かめる意味もない
- **何が起きているか**: 学ぶ側の SIGReg は 32 本のストリーム（9 本の動画）の間の違いで満たされる。$z$ は場面の色・明るさ（どの動画か）を持ち、1 本の動画の中の違い（建物、道、人）を持たない。トークンの予測は、隠したトークンを場面の平均で当てれば `pred` が下がる。SIGReg を強めると、$z$ は学ぶ 9 本を見分ける向きにだけ広がり、Zurich に移らない
- **評価の側の注意**: ViT の符号は学ぶ側と val の差が大きい（学習前でも `recon_fit` 0.32 と val 0.63）。デコーダは 2048 個の窓（各 9 積み、場面は 2048 か所）から学ぶので、場面を覚えられる。PCA には差がない。符号の比較は val の値で行っているので判断は変わらないが、デコーダの学ぶ窓を増やすと ViT の値は少しよくなりうる

次に決めること（ユーザーの判断が要る。どれも規則「再構成の項なし・EMA なし」の中）:

1. **予測を $z$ の水準でも行う**（LeJEPA の形）: 今は SIGReg を pool した $z$ にかけ、予測はトークンごと。$z$ は予測の損失を直接受けない。context view の $z$ から target view の $z$ を当てる項を足せば、$z$ が場面の中の違いを持つ向きに押される
2. **pool を学ぶ**（attentive pooling、V-JEPA の probe の形）: $z$ は 1 本のベクトルのまま。今の packed は平均の pool だけ
3. **短い run・低い学習率**: 最良のチェックポイントがいつも 300 秒なので、学習率 3e-5〜1e-4 と 300〜600 秒を探す。ただし学習前を下回った run は無く、学習で得をしている証拠はまだない

study を今の形で回すなら、範囲は次を勧める: `vision.sigreg` [0.02, 0.3]（log。0.9 は val を悪くした）、`vision.sigreg_on` {z, both}（both が最良、$J$ 1.42）、`optim_vision.lr` [3e-5, 1e-4]（3e-4 は悪い）、`vision.sg` false、マスクは V-JEPA のまま（0.15・0.7。小さくしてもよくならない）、`vision.frames` {8, 16}、`vision.stride` {2, 3, 6}、`seconds` 600、目的は最後のチェックポイント。

## 診断（2026-11-12、BP、seed 100）

方針の見直し（MILESTONES.md の M17）を受けて、試しの no-go の原因を切り分けた。腕は 4 つ。

- A: 既知の基準の課題（Imagenette）で、私たちの ViT・SIGReg・optimizer が学べるか
- B: ストリームか i.i.d. か
- C: 学習率と warmup
- D: 目的の式（トークンの予測、時空間の補完、EMA と LN + sg の対照）

どれも BP、seed 100、600 秒。$N=16$ の 6 本（D と、B の時空間の版）のほかは $N=8$。設定は「監査を受けた直し」の後の preset で、トークンの SIGReg は `clip` にしてある。「何が分かれば何と言えるか」は回す前に次のように決めた。A で学習前より 30 ポイント以上上がらなければ、部品に不具合がある。B で i.i.d. だけが下がるなら、原因はストリームの相関にある。C で学習率を下げたほうが良くなるなら、学習率が高すぎた。

コード: run と posthoc は snapshot `dfaa437`、`m17-dx-n8-v2` とその posthoc、Imagenette の 2 本（`nocolor`・`masked-z-lr3e-4`）は `a9cfa9d`（`--no_color` を足した後）。どちらも `d86a328` の上で、mujou は `7a8b72e`（origin にある）、データは `3c3e6805fdaa`。ホストは std-00・02・03 の 4090 と 4060。std-01 は `just fleet doctor` で健全と出た。ただし cordon のまま WT のデータも無いので、Imagenette だけに使った（fleet の外で手で起動）。

### 結論

- **不具合はあった。主因は直した 2 つ（積みの中のトークンの崩壊と、補完の誤差の正規化）だった**。直した後の preset のトークンの予測では、held-out の Zurich の補完の誤差（`ncomp`）が学ぶほど単調に下がる（EMA と LN + sg の対照を除く）。値は学習前のネットワーク（1.65〜1.76）と、自明な予測（見えるトークンの平均 `_vis` 1.06〜1.23、学ぶ側の平均 `_mean` 約 1.2）のどちらよりも小さい。600 秒の時点でもまだ下がっている。held-in（`fit_`）と held-out の差は −0.01〜0.06 で、学ぶ 9 本の場面を覚えているだけではない。学習率 1e-4 以下のトークンの予測の腕では、posthoc の `recon` も学習前より良く、300 秒から 600 秒にかけて良くなる（試しの「最良は 300 秒、その後は悪くなる」は消えた）
- **学習率は高すぎたのではなく、低すぎた**。補完の誤差は学習率とともに単調に良くなる（$N=8$、短い範囲の val: 1e-5 で 0.85、3e-5 で 0.64〜0.69、1e-4 で 0.41〜0.48、3e-4 で 0.19）。warmup は 0 か 6000 step（600 秒の 1/3）かで差が小さく、6000 のほうが少し良い。cosine の減衰を外すと（一定の 1e-4）0.27 まで下がる。`adamw_step` の preset の cosine は 18000 step（1 step ≈ 1 フレームの見積もり）で peak の 1e-3 倍に着く。BP が `time.learn_interval` の 25 ms ごとに学ぶなら、run は約 24000 step 学び、最後の約 4 分の 1 は最小の学習率で進む（step の数は確かめていない。checkpoint に optimizer の状態が無い）
- **ストリームか i.i.d. かは効かない**。同じ目的で、短い範囲の val は 0.525 と 0.511（$N=8$）、時空間の版の `zcomp` は 0.091 と 0.086 だった
- **部品は学べる**。Imagenette の LeJEPA（色の拡張つきの view）では、私たちの ViT・`exp.lib.sigreg`・`StepAdamW` で、線形 probe が学習前の 40.7% から 78.5% に上がった（+37.8 ポイント、合格の目安 +30）。BP で学べない設定ではない
- **限界は目的の式（拡張のない view とマスク）にある**。同じ ViT と Imagenette でも、マスクした view（M17 の packed の形、拡張なし）では、$z$ の補完が 55.9%（+15）、トークンの予測が 47.6%（+7、学習率 3e-4）にとどまる。学習率 2e-3 では 25.8% で、学習前より悪い。LeJEPA から色の拡張だけを外すと 64.1%（-14.4 ポイント）。WT でも、どの腕の posthoc の `recon` も 0.53〜0.74 で、PCA-256（0.180）に遠い。デコーダの像は場面の色と明暗の配置（上が空、下が地面）までで、建物・人の輪郭は出ない。`dyn_1/copy_1` は 0.72〜0.99 で、学習前（0.51）より悪い
- **補完の損失だけでは表現の良さを測れない**。Imagenette では、学ぶにつれて損失は下がり続けるのに、probe は止まる（$z$ の補完: 損失 0.25→0.14 の間に probe 55.7→55.9%。トークン: 0.98→0.59 の間に 47.4→47.6%）。WT の学習率の列では、1e-4 までは `ncomp` が小さい腕ほど posthoc の `recon` も小さかった。ところが 3e-4 では、`ncomp` が一番小さい（0.19）のに、`recon` は 300 秒の 0.578 から 600 秒の 0.614 に悪くなった（val）。補完の誤差が小さいことは必要だが、それだけでは足りない
- EMA（0.996）と、target の LN + sg は、どちらも補完の誤差・`recon` ともに悪くした（ランクだけは 9〜10 に上がる）

### 判断と次の study への推奨

1. **原因**: 試しの no-go の主な原因は不具合だった（SIGReg が $z$ だけにかかり、トークンが積みの中でつぶれる。それを補完の誤差の分母が隠していた）。学習率は高すぎず、むしろ低かった（step で 7.5e-5 より 1e-4 以上が良い）。warmup とストリームは主因ではない。BP で学べない設定でもない（Imagenette の LeJEPA で +38 ポイント）。ただし、直した後でも、拡張のない view とマスクからの補完で取れる特徴は粗い（Imagenette で +7〜15 ポイント、WT の `recon` は PCA の 3 倍）。残っている差の主因は目的の式（拡張の無さ）とみる
2. **次の study の設定（推奨）**: `+experiment=m17/wt_n8`（または `wt_n16`）に `optim@optim_vision=adamw_step optim_vision.warmup_steps=6000`、`optim_vision.decay=constant`（継続学習には終わりが無いので、V-JEPA 2 の warmup-constant の形）、学習率は [5e-5, 3e-4]（log）。3e-4 では補完の誤差が下がり続けるのに `recon` が悪くなったので、上の端は posthoc を見て決める。トークンの SIGReg は `clip` のまま。ストリームのままでよい（i.i.d. は要らない）。EMA と LN + sg は使わない。時空間にするために、context の view に未来の view（`{blocks: 8, scale: 0.15, future: 2}`）を足す。$z$ の水準の補完（`st_tok`）はランクを上げるが補完の誤差と `recon` を悪くしたので、軸として残す（`vision.z_weight` {0, 1}）
3. **まだ実装していない、効きそうなもの**: view ごとの色の拡張（Imagenette で LeJEPA の probe を 14.4 ポイント上げた）。WT の色の近道を塞ぐので、次の study の前に足すことを勧める
4. **study の目的の案（ユーザーが決める）**: 潜在空間でマスクを予測する損失そのものを held-out で測る（MILESTONES.md の決定）。そのまま `pred` を使うと、トークンを縮めれば小さくなる。そこで、積みの中の広がりで割った次の版を案とする。

$$
J_{\mathrm{comp}} = \log \frac{1}{|K|} \sum_{k \in K} \mathrm{ncomp}_k,\qquad \mathrm{ncomp}_k = \frac{\sum_{i}\sum_{t \in \Omega_{i,k}} \lVert \hat s_{i,t} - s_{i,t} \rVert^2}{\sum_{i}\sum_{t \in \Omega_{i,k}} \lVert s_{i,t} - \bar s_{i} \rVert^2}
$$

  ここで $K$ = {短い範囲, 長い範囲, 未来}、$\Omega_{i,k}$ は積み $i$ で隠したトークン、$\bar s_i$ は積み $i$ の target のトークンの平均（val、Zurich）。崩壊・非有限は $\log 10$。加えて、`tok_within` / (`tok_within` + `tok_between`) < 0.1 か `z_spread` < 1e-3 なら $\log 10$ にする（積みの中のつぶれと $z$ の崩壊の見張り）。今の `measure.encoder_objective=completion` は `comp`（積みの間で割る）なので、`ncomp` に替える必要がある。注意: Imagenette では、損失が下がり続けても probe が止まった。$J_{\mathrm{comp}}$ は同じ目的の族の中で設定を選ぶのに使える見込みがある（WT の学習率の列では 1e-4 までは `recon` と同じ順だったが、3e-4 で外れた）。ただし、目的の式（$\beta$、$\alpha$、view）をまたいで比べると、target が違うので公平でない。目的の式を探索の軸に入れるなら、posthoc の `recon_blur` を並べて見る
