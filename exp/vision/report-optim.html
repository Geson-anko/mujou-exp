流れ続ける動画から学ぶとき、どの optimizer を使えばよいか

街を歩きながら撮った動画を 1 枚ずつ流し、誤差逆伝播を使わない学習則 PC-ALM で VAE を学ばせました。前の資料（V0〜V10）では、RMSProp なら学べて、SGD では学べないことが分かりました。この資料では、その理由を optimizer の側から調べた V11〜V15 の結果をまとめます。

結論

分かったこと

V11・V12

学べるかどうかは、optimizer の種類では決まらない

SGD でも、デコーダの学習率だけを 100 分の 1 にすると学べました（3 つの seed で span 0.664〜0.771）。反対に、RMSProp でデコーダの学習率を 10 倍にすると、SGD と同じように学べなくなりました（span 1.681）。

V15

決め手は、デコーダの重みが 60 秒でどれだけ動くか

デコーダの重みが 60 秒で 1.4% 未満しか動かない run では、27 本のうち 26 本でデコーダが z を使いました。6% 以上動く run では、15 本のうち 1 本だけでした。optimizer の種類によりません。

V14

μP なら、よい学習率は幅によらない

μP では、4 つの幅のすべてで、τ = 3·104 が最もよいか、最もよいものと区別できない点でした。通常の設定（SP）では、よい τ が幅とともに 10 倍ずれました。幅を広げるほど誤差は小さくなり、最小は幅 1024 の 0.587 でした。

V13・V15

新しく試した 2 つの方法は、RMSProp を超えなかった

勾配を直交させる方法（OGD）を入れると、RMSProp と AdamW は学べなくなりました。重みの動く速さを秒で決める optimizer（Angular）は学べましたが、最もよい span は 0.802 で、RMSProp の 0.708 に届きませんでした。どちらも mujou には加えません。

1

実験の仕組み

入力は、街を歩きながら撮った動画（Walking Tours の Amsterdam）です。動画は 1 枚ずつ流れ続け、モデルは流れてきた画像でその場で学びます。この流れをストリームと呼びます。0.1 秒ごとの 8 枚の画像（64×64 ピクセル）を 1 組にしたものを stack と呼びます。stack は 0.1 秒ごとに 1 つ届き、同じ stack が 2 度来ることはありません。1 本の run は 1800 秒（18000 stack）です。

モデルは VAE で、8 つのノードに分かれています。エンコーダ（ViT-S を 4 つに分けたもの）が stack を潜在変数 z（256 次元）に写し、デコーダが z から最後の 1 枚を描き戻します。各ノードは、隣のノードと値と誤差だけをやり取りし、0.1 秒に 1 回、自分の誤差で重みを更新します。optimizer はノードごとに置き、ほかのノードの状態は見ません。

学習率の表し方

この実験では、学習率を時定数 τ（秒）で表します。0.1 秒の更新 1 回で、重みは 0.1/τ に比例して動きます。τ が大きいほど、ゆっくり学びます。RMSProp と AdamW では、各重みが 1 回に動く量がほぼ 0.1/τ になります。SGD では、動く量が勾配の大きさにもよります。

指標の読み方

誤差は、どれも「どの入力にも平均の stack を出したときの誤差」を 1 とする比で表します。1 を下回れば、平均の画像を出すより良いということです。

span
学習に使った区間（0〜1800 秒）から 5 秒ごとに stack を選び、学習しているモデル（エンコーダ → z → デコーダ）で描き戻したときの誤差です。小さいほど良い。この研究の順位はこの値で決めます。
after
1800 秒より後の、まだ見ていない区間での同じ誤差です。
今の誤差
1800 秒の時点で流れていた stack の誤差です。モデルが今の場面をどれだけ描けるかを表します。
忘却
10〜60 秒前、60〜300 秒前、300 秒より前に流れた stack について、今の誤差から、流れたときの誤差を引いたものです。小さいほど忘れていない。負なら、流れたときより今のほうがよく描けます。
recon_blur
学習を止めたエンコーダの z から、別に学んだデコーダで画像を描き戻したときの誤差です（ぼかした画像どうしで比べます）。小さいほど、z に入力の情報が残っています。
dyn_1/copy_1
z の 0.1 秒先を線形の式で予測したときの誤差を、「変わらない」と予測したときの誤差で割ったものです。小さいほど、z の動きを予測しやすい。
学べた（4 条件）
1800 秒の時点で、次の 4 つをすべて満たした run を「学べた」とします。(1) span が 0 秒の値より小さく、1 より小さい。(2) after が 0 秒の値より小さい。(3) recon_blur の下がり幅が、標準誤差を合わせたものの 2 倍より大きい。(4) dyn_1/copy_1 が 0 秒の値より小さい。V8 で決めた条件です。
z の差
デコーダが z を使っているかを調べる値です。各 stack を、その stack の z と、900 秒離れた別の場面の z の 2 通りで描き戻し、span の差をとります。0.2 を超えれば z を使っている、0.05 未満なら使っていないとみなします。使っていなければ、どの z を入れても同じ画像が出るので、差は 0 になります。
1 フレームの一歩
1 回の更新で、ノードの重みが自分の大きさの何割動いたか（‖Δθ‖/‖θ‖）を 300〜1800 秒で平均したものです。この資料では、その速さで 1 ラジアン回るのにかかる秒数に直して示します。
60 秒の変位
60 秒ごとに保存した重みを比べ、60 秒のあいだに重みが正味でどれだけ動いたか（‖θ(t+60) − θ(t)‖/‖θ(t)‖）を 300〜1800 秒で平均したものです。エンコーダ全体とデコーダ全体の、行列の重みについて求めました。
μP
モデルの幅を変えても、よい学習率が変わらないように、初期化と層ごとの学習率を幅に合わせて決める方法です（Tensor Programs V）。幅 256 では通常の設定（SP）と同じになります。

V11〜V15 のどの段でも、順位は 4 条件を満たした run の 1800 秒の span で決めます。V10 では、同じ設定で seed だけを変えた 3 本の span が 0.708〜0.778 に散らばりました。そこで、seed 1 本どうしの比べでは、差が 0.07 より小さいものは区別しません。

3 · V11

どの optimizer なら学べるか

問い　PyTorch にある基本の optimizer のうち、どれならストリームで学べるか。前の資料の見立て「重みごとに一歩の大きさをそろえると学べる」は正しいか。

条件　ViT-S から optimizer だけを変えました。seed 0、1800 秒。基準の 3 本（SGD・RMSProp・AdamW）は V8 と同じ設定です。勾配の統計も記録しましたが、学習の経過は V8 とビット単位で同じでした。

図から読めること

  • 4 条件を満たしたのは、RMSProp τ = 104（0.708）、RMSProp（centered）τ = 104（0.715）、AdamW τ = 105（0.760）の 3 本です。3 本の差は 0.07 より小さく、区別できません。
  • Adadelta と Rprop は、どの τ でも学べませんでした。どちらも重みごとに一歩をそろえる optimizer です。Adadelta の span（1.671〜1.692）は、SGD（1.675）とほぼ同じでした。
  • Muon τ = 104 の span（0.649）は全 run で最も小さい値でしたが、dyn_1/copy_1 が下がらず（0.994 → 1.004）、条件 (4) で外れました。
  • 学べなかった run の多くは、z の差がほぼ 0 です。デコーダが z を使っていません。

分かったこと　「重みごとに一歩をそろえれば学べる」という見立ては成り立ちませんでした。回す前に決めた反証の条件（Adadelta と Rprop がどちらも学べない）に当たります。

4 · V12

デコーダだけを遅くすると、SGD でも学べるか

問い　SGD のデコーダは、z を使わず、自分の重みを書き換えて今の場面を描いています（V8）。デコーダの学習率だけを下げて、重みで場面を追えないようにすると、デコーダは z を使い始めるか。

条件　デコーダ（dec1・dec2・out）の τ だけを dec_scale 倍にしました。dec_scale は 0.1、1、10、100 です。1 は V11 の基準の run です。seed 0、1800 秒。

図から読めること

  • SGD は、デコーダを 100 倍遅くすると学べました（0.703）。RMSProp τ = 104（0.708）と区別できません。10 倍では、かえって悪くなりました（1.876）。
  • RMSProp は、デコーダを 10 倍速くすると学べなくなりました（1.681）。この値は SGD（1.675）とほぼ同じです。100 倍遅くすると、遅すぎて学べませんでした（2.790）。

分かったこと　学べるかどうかは、optimizer の種類より、デコーダの重みがどれだけ速く動くかで決まっています。デコーダが速いと、デコーダは今の場面を自分の重みで覚え、z を使いません。

5 · z_use

デコーダは z を使っているか

問い　span が 1 を下回っても、デコーダが z を使っているとは限りません。今の場面を重みで覚えるだけでも、平均の画像よりは良く描けるからです。そこで、z を入れ替えて、デコーダが z を使っているかを直接調べました。

条件　V11 と V12 の 1800 秒のモデルです。各 stack を、正しい z、900 秒離れた stack の z、全 stack の z の平均の 3 通りで描き戻しました。

図から読めること

  • 学べなかった SGD 系の run（SGD、Nesterov τ = 105、Adadelta、RMSProp（centered）τ = 103、デコーダを速くした RMSProp）では、z を入れ替えても誤差が ±0.003 しか変わりません。デコーダは z をまったく使っていません。
  • span が 1 を下回った 6 本と Muon τ = 104 では、z を入れ替えると誤差が 0.69〜0.86 増えます。デコーダは z を使っています。
  • Rprop τ = 104・105、Muon τ = 103、デコーダを 100 倍遅くした RMSProp は、z を使い始めています（+0.25〜+0.60）が、span は 1 を下回りません。学ぶのが遅いためです。
6 · V13

勾配を直交させると、忘れにくくなるか

問い　直近に保存した勾配と直交する向きにだけ重みを動かすと（OGD）、忘れにくくなり、span は小さくなるか。

条件　V11 の基準の 3 本に OGD を加えました。直近 16 本の勾配を、s 秒ごと（s = 0.1、1、10）に保存します。seed 0、1800 秒。

図から読めること

  • OGD を入れると、RMSProp と AdamW は学べなくなりました（span 3.0〜4.9）。今の場面の誤差も 4〜7 に残り、1800 秒かけても平均の画像より悪いままです。
  • ストリームでは、直近の勾配こそが今下るべき向きです。OGD はこの向きを取り除くので、重みがほとんど動かなくなります。
  • RMSProp の 10〜60 秒の忘却は、0.28 から 0.14〜0.18 に下がりました。ただし、ほとんど何も学んでいないので、忘れにくくなったとは言えません。

分かったこと　OGD は効果がありませんでした。ストリームには「タスク」の区切りがなく、勾配の相関も 10 秒でほぼ消えるので、研究の依頼者の判断で、OGD はこの研究から外しました。

7 · V14

モデルの幅を変えると、よい学習率は変わるか

問い　モデルの幅を変えると、よい τ は変わるか。μP にすると、幅によらず同じ τ がよくなるか。

条件　RMSProp で、幅 128・256・512・1024、τ = 103〜105 の 5 点を、SP と μP で回しました（幅 256 は SP と μP が同じ）。35 本、seed 0、1800 秒。

横軸は τ（右ほどゆっくり学ぶ）、縦軸は 1800 秒の span（下ほど良い）です。線の色が幅です。塗りつぶした点は 4 条件を満たした run、白抜きの点は満たさなかった run です。

幅 128幅 256幅 512幅 1024

各幅の最もよい τ（4 条件を満たし、span が最小のもの）と、その span です。括弧内は、最もよいものと 0.07 以内で区別できない τ です。

図と表から読めること

  • μP では、最もよい τ が 4 つの幅すべてで 3·104 か、その隣の 105 でした。幅 1024 でも、3·104（0.633）は最もよい 105（0.587）と区別できません。
  • SP では、最もよい τ が幅 128 の 104 から幅 1024 の 105 まで、10 倍ずれました。同じ τ = 104 でも、SP は幅 512・1024 で学べませんでしたが（1.217、1.587）、μP は学べました（0.715、0.917）。
  • 幅を広げるほど span は小さくなりました。最小は幅 1024 の μP、τ = 105 の 0.587 で、V11〜V15 の全 run で最も小さい値です。
  • 幅 256（ViT-S）では、τ = 3·104 の 0.635 が、これまでの基準の τ = 104（0.708）より小さくなりました。差は 0.073 で、区別の目安の 0.07 をわずかに超えるだけです（seed 1 本）。
  • τ = 105 は、幅 1024 を除いて条件 (4) で外れました。τ ≤ 3·103 では、どの幅でもデコーダが z を使いません。

分かったこと　μP にすれば、よい学習率を幅 256 で決めて、ほかの幅にも使えます（muTransfer）。seed は 1 本なので、まだ確かめきれていません。

8 · V15

エンコーダとデコーダの速さを直接決めると

問い　V12 では、デコーダの速さを optimizer ごとに観測しただけでした。速さそのものを設定にして変えると、デコーダが z を使うかは、デコーダの速さだけで決まるか。学べるのは、どの速さの組み合わせか。

道具　Angular という optimizer を作りました。行列の重みは、勾配の移動平均（時定数 1 秒）の向きに、自分の大きさの 0.1/τ だけ動きます。動く割合が勾配の大きさによらず決まるので、τ は「行列が約 1 ラジアン回るのにかかる秒数」になります。行列でない重み（バイアスなど）は RMSProp で動かします。

条件　エンコーダの τ（Tenc）を 100・300・1000・3000 秒、デコーダの τ（Tdec）を 30〜10000 秒の 6 点にしました。24 本、seed 0、1800 秒。

図から読めること

  • デコーダの τ が 100 秒以下の 8 点では、デコーダは z をほぼ使いません。例外は、エンコーダが最も遅い 3000 秒・100 秒の点（+0.225）だけです。
  • デコーダの τ が 300 秒の列では、エンコーダが速い（100・300 秒）と z を使わず、遅い（1000・3000 秒）と使います。デコーダの速さだけでは決まりません。
  • 4 条件を満たしたのは 6 点です。外れ方は 3 通りあります。デコーダが速すぎる（z を使わない）、エンコーダが遅すぎる（3000 秒の行。条件 (4) で外れる）、デコーダが遅すぎる（10000 秒の列。span が 1 を下回らない）です。
  • 4 条件を満たした点で最も小さい span は、1000 秒・1000 秒の 0.802 です。RMSProp τ = 104（0.708）より 0.094 大きく、Angular は RMSProp を超えませんでした。
9 · V11・V12・V15

速さは「1 フレームの一歩」ではなく「60 秒の変位」で測る

問い　V12 では、1 フレームの一歩から求めたデコーダの速さで、z を使うかどうかが分かれるように見えました。V15 の格子でも、同じ測り方で分かれるか。

条件　V11・V12・V15 の、完走した 49 本です（V15 の seed の 4 本を含みます）。左の図は 1 フレームの一歩から求めた dec2 の速さ、右の図はデコーダ全体の 60 秒の変位を横軸にしました。

点 1 つが run 1 本です。縦軸は z の差で、上ほどデコーダが z を使っています（破線は 0.2 と 0.05）。左の横軸は dec2 が 1 ラジアン回るのにかかる秒数（右ほど遅い）、右の横軸はデコーダの重みが 60 秒で動いた割合（%、左ほど遅い）で、どちらも対数です。色は optimizer の種類です。本文で比べる 2 本の点には、図の中に名前を書き添えました。点に触れると値が出ます。

図から読めること

  • 左の図では、Angular（Tenc = Tdec = 300 秒）と RMSProp τ = 104 の速さがほぼ同じ（576 秒と 603 秒）なのに、Angular のデコーダは z を使わず（−0.002）、RMSProp のデコーダは使っています（+0.724）。1 フレームの一歩では、optimizer をまたいで比べられません。
  • 右の図では、同じ 2 本が離れます。60 秒の変位は、Angular が 4.1%、RMSProp が 1.3% です。
  • 右の図で、デコーダの 60 秒の変位が 1.4% 未満の 27 本のうち 26 本が z を使いました（例外の Muon τ = 105 は、遅すぎて何も学べていません）。6% 以上の 15 本では、z を使ったのは 1 本（+0.225）だけでした。2〜5% の 7 本では、エンコーダが遅い run ほど z を使いました。

なぜ違うのか　Angular は勾配の移動平均の向きに進むので、続くフレームの一歩がほぼ同じ向きに積み重なります。RMSProp は生の勾配の向きに進みます。隠れ層の勾配はフレームごとにほぼ無相関なので、一歩どうしが打ち消し合います。そのため、1 フレームの一歩が同じでも、60 秒で正味に動く量は Angular のほうが約 3 倍大きくなります。

分かったこと　デコーダが z を使うかどうかは、optimizer の種類によらず、場面が変わる時間（数十秒）のあいだにデコーダの重みが正味でどれだけ動くかで、ほぼ決まります。60 秒で 1% 程度まで遅ければ使い、6% 以上動けば使いません。その間では、エンコーダの速さも影響します。

seed を変えても同じ結果になるか

条件　それぞれ seed 1・2 を加えました。RMSProp τ = 104 の 3 つの seed（V8）と並べます。

図から読めること

  • デコーダを 100 倍遅くした SGD は、3 つの seed すべてで学べました（平均 0.713）。RMSProp τ = 104 の 3 つの seed の平均（0.741）と区別できません。

11

予想の判定

回す前に README に書いた予想と、その判定です。判定の基準（4 条件、z の差の 0.2 と 0.05、区別の目安の 0.07）も、回す前に決めました。

次の実験で使うものと、残る課題

次の実験で使うもの　optimizer は RMSProp のままにします。幅を変えるときは μP を使い、τ は幅 256 で決めます。評価には、4 条件に加えて z の差と 60 秒の変位を記録します。

まだ分からないこと

  • ViT-S の τ を 3·104 に変えるべきか。差は 0.073 で、seed 1 本の比べです。seed を加えて確かめます。
  • デコーダの 60 秒の変位を、直接決められるか。決め手が分かったので、それを設定にする optimizer が考えられます。Angular は 1 フレームの一歩を決めたため、正味の動きは決められませんでした。
  • 原因と結果の区別。60 秒の変位は、300〜1800 秒で測った量です。デコーダが z を使うかは、最初の数十秒で決まっているのかもしれません。z を使わないデコーダは今の場面を重みで追うので、重みがよく動く、という逆向きの関係もありえます。V15 では速さを設定で変えたので、その範囲では速さが原因と言えます。
  • エンコーダが遅いと、なぜ条件 (4) で外れるのか。エンコーダの 60 秒の変位が約 0.5% 以下の run で、dyn_1/copy_1 が下がりませんでした。
